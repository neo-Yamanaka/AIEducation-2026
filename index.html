Generative AI  ×  Claude Code

AIと、 賢く付き合う技術。

生成AIは一瞬でコードを生む。けれど、前提を間違えたまま走ることもある。このサイトは、品質を保ちながらAIと開発を進めるための「ルール」と「実践テクニック」を、用語解説つきで一気に学べる場所です。

00 — Foundation

まず、土台の3つ。

細かいルールに入る前に、この3語だけ押さえておけば全体が読めます。下線つきの用語は、ホバー（スマホはタップ）で意味が出ます。

i.

生成AIとは

文章やコードを自動で作り出すAI。プロンプト（指示文）を与えると、それに沿った出力を返してくれます。ChatGPT や Claude がその代表です。

ii.

AI駆動開発とは

生成AIに実装や調査・レビューを任せながら進める開発スタイル。速い反面、「どこまで任せ、どこを人が確認するか」の設計が品質を分けます。

iii.

Claude Codeとは

Anthropic の Claude に、コードの読み書きやコマンド実行まで任せられる開発ツール。ターミナル・VS Code などのエディタ・デスクトップアプリ・ブラウザで使えます。ルールファイルやスキルで、AIに前提を毎回読ませて作業させられます。

Part Ⅰ — Rules

守るべきこと（1〜6章）

ツールに依存しない、普遍的な運用原則。チームで共有する前提として読んでください。

01

ルール・方針の統一

Unify the rules

AIを使う開発では、人ごとに指示の出し方が違うと、コード品質や設計がそろわなくなります。チームであらかじめ共通ルールを決め、AIにも同じ前提で作業させます。

明文化したいコーディングルール

  • 命名規則 / ディレクトリ構成（＝フォルダの置き方）
  • コメントの書き方 / エラーハンドリング方針
  • テスト方針、そして「誰がどのファイルを触るか」の担当範囲

AIへの前提指示（設計方針）

  • 勝手に既存仕様を変えない／推測だけで実装しない
  • 不明点は確認する／影響範囲を調べてから直す
  • 指示された範囲外を直さない／大きな変更は実装前に方針を提示する
Whyこうした前提を先に渡すことで、AIの「やりすぎた修正」や意図しない変更のリスクを下げられます。
02

ルールの集約と共有

Centralize into rule files

1章で決めたルールは、持っているだけでは効きません。ルールファイルとして、AIが毎回自動で読み込む場所に置いて初めて実効性を持ちます。

代表的なルールファイル

  • CLAUDE.md（Claude Code）／ AGENTS.md（複数のAIツールで共通の形式）／ .cursor/rules/（Cursor。旧形式の .cursorrules は非推奨）
  • ドメイン固有のルールは .claude/rules/*.md に分け、先頭の paths: で対象パスを指定すると、そのファイルを触ったときだけ読み込まれる
  • 決まった作業手順（リリース手順・レビュー観点など）はスキル（.claude/skills/）にして、必要なときだけ読ませる

運用のコツ

  • ファイルはシンプルに保つ（CLAUDE.md は200行程度までが目安）。詰め込みすぎると毎回の読み込みトークンが増え、肝心のルールが埋もれる
  • 全体に効かせたいルールは先頭に、特定分野のルールは分離する
  • 重要な方針は「レビュー時に必ず確認する観点」としても書いておくと、節目ごとにチェックされてブレにくい
  • Claude Code は、CLAUDE.md があると AGENTS.md を読みません。他ツールと共用するなら AGENTS.md を正本にし、CLAUDE.md に @AGENTS.md と1行書いて取り込むのが確実（Windows ではシンボリックリンクより安全）
MemoryClaude Code には、AIが作業中に学んだことを自分でメモして次回に活かす自動メモリもあります。ただしこれは個人の手元に残るメモ。チームで守るルールは必ず CLAUDE.md 等に書いてリポジトリで共有しましょう。
03

セキュリティ・機密情報の取り扱い

Security & secrets

AIにコードやデータを渡す開発では、安全面のルールを最初に決めます。特に個人情報や認証情報を扱うシステムでは重要度が高いです。

  • 機密情報（APIキー・.env・本番データ等）をAIのコンテキストに渡さない
  • プロンプトインジェクションに注意。外部から取り込んだ文章は「データ」として扱わせる
  • コマンド自動実行は許可/拒否リストで制御。rm・git push・.env読み取り等はAIによる自動実行を拒否し、必要なときは人が内容を確認してから実行する
  • AIが勧めるライブラリは実在する正規品か確認（パッケージハルシネーションはサプライチェーン上のリスク）

「お願い」ではなく「設定」で止める

CLAUDE.md に「.env を読まないで」と書いても、それはお願いにすぎず、AIが従わないことがあります。絶対に守らせたいことは、Claude Code の設定で仕組みとして止めます。設定はリポジトリの .claude/settings.json に置けば、チーム全員に同じ制限がかかります。

  • 拒否ルール（permissions.deny）… 例："Read(./.env)"・"Read(./secrets/**)" を登録すると、読み取りも編集もブロックされる
  • フック（Hooks）… ツール実行の直前などに決めたスクリプトを走らせ、rm -rf や本番DBへの接続といった危険な操作をその場で止める。編集後に自動でフォーマッタをかける用途にも使える
  • 権限モード… 操作ごとに確認する／編集は自動承認する／計画だけ立てる、などを切り替えられる。全操作を無確認で通すモードは、隔離した検証環境以外では使わない
Caution「AIが勝手に破壊的な操作をした」という事故の大半は、権限と機密情報の扱いをルール化していないことが原因です。なお、コマンドの書き込み先や通信先を OS レベルで制限する「サンドボックス」は macOS / Linux / WSL2 向けで、Windows ネイティブ環境では使えません。Windows 中心のチームほど、拒否ルールとフックをしっかり設定しておきましょう。
04

データベース設計・変更管理

Database changes

AIが「必要だ」と判断して勝手にテーブルを増減したり、スキーマを変えたりすると、既存機能や他メンバーの作業に大きく影響します。DB設計は後戻りが難しいぶん、慎重に。

  • テーブルの追加・削除は事前承認制にする
  • カラムの追加・変更・削除はレビュー対象にする
  • マイグレーションファイルの内容を必ず確認する
  • 既存データへの影響を事前に確認／複数人開発では承認フローを設ける
PrincipleAIの提案をそのまま採用せず、人間による確認を必須に。
05

ソース修正をAIに任せる際の作業ルール

Editing workflow

修正前後の基本フロー

修正前…対象の仕様・既存コードの構造・影響範囲をAIに確認させる。
修正後…テスト実行・差分確認・不要な変更が無いかをチェック。

  • 頼んでいないリファクタリングをさせない
  • 実装内容をAIに説明させ、作業者自身が理解する
  • タスクごとに完了の定義（DoD）を先に決める

テストの健全性を守る

AIはテストを通すために、テスト自体を弱めたり消したり、自明にパスする内容へ書き換えることがあります。

  • 既存テストを勝手に変更・削除させない
  • バグ修正は、先に「失敗するテスト」を書かせてから直させる
  • リグレッションテストを残し、何を保証しているか把握する

バージョン管理・PR運用

  • タスク単位でブランチを切り、コミットは小さく
  • AIに自動コミットやforce-pushをさせない
  • レビューはPRの差分ベースで行う
Nextこの「確認してから直す」流れは、実践編の A「意図を固める」（プラン承認・計画モード） でさらに具体化できます。
06

AI出力との向き合い方

How to treat AI output

AIを使うと、内容を理解しないまま開発を進められてしまう落とし穴があります。生成コードをそのまま使うと、問題発生時の原因調査や修正が難しくなります。

  • AIに実装内容を説明させ、自分で理解してからマージする
  • 重要・複雑な処理は人によるレビューを必須にする
  • ハルシネーションに注意。見覚えのないAPIや設定は公式ドキュメントで裏取り（MCP等で最新仕様を参照させる）
In shortAIの出力は「たたき台／補助的な提案」。最終判断は人間が行う、を前提に。下の信頼度メーターで体感し、実践編の B「品質を高める」 で裏取りの具体策（MCP等）へつなげましょう。
Signature — Trust Calibration

どこまで信用する？

AI開発で最も難しい問いのひとつ。スライダーを動かして、信頼度の「ちょうどいい」を体感してください。

信用しなさすぎちょうどいい信用しすぎ
050100
確認作業が多すぎる
出力を疑いすぎると、確認に時間がかかりAIを使うメリットが小さくなります。スライダーを右へ動かしてみましょう。
Part Ⅱ — Practice

実践テクニック（4つの視点）

日々の開発を効率化・高品質化する具体策を、意図を固める・品質を高める・スケールさせる・コストを抑えるの4つの視点で整理しました。Claude Code での開発をベースに説明していきます。

A

意図を固める

Align intent first

AI開発で最も手戻りが出るのは「頼んだつもり」と「作られたもの」のズレ。実装に入る前に、方針・範囲・手順を握っておくのが、いちばん効きます。

プラン承認 ＆ 計画モード

いきなり実装させず、先に方針・影響範囲・手順を提示させ、人が承認してから着手させます。計画モードを使うと、AIは読み取り・調査だけを行い、ファイルを書き換えずに計画を立てます。承認するまでファイルが書き換わらないので、意図ズレを未然に防げます。Claude Code では Shift+Tab でモードを切り替えるか、/plan で計画モードに入れます。

Why先に計画を挟むと、間違った方向へ大量のコードが生成される事故を防げます。仕様を先に固める spec駆動 も同じ発想で、手戻りと無駄なトークン消費を減らせます。

対話で要件を掘り下げる

重要な作業ほど、いきなり作らせず対話で要件を詰めます。次の一文を添えるだけでも精度が変わります。

  • 「推測での実装を避け、不明点は先に質問してください」
  • 「実装の前に、方針と影響範囲を箇条書きで見せてください」
  • 「この理解で合っているか、作業前に確認させてください」

止める・戻す — 軌道修正の基本

「間違っても止めて戻せる」と知っておくと、安心して任せられます。

  • 方向がズレたと感じたら ESC でいつでも中断し、指示を出し直す（最後まで待つ必要はない）
  • Claude Code はファイル変更前の状態をチェックポイントとして自動記録。/rewind（または入力欄が空の状態で ESC を2回）で、コード・会話のどちらか、または両方を変更前に巻き戻せる
Safety netチェックポイントは便利な安全網ですが、万能ではありません。シェルコマンド（rm・mv など）による変更や、サブエージェントによる編集は巻き戻せません。コミットやブランチによる正式なバージョン管理（5章）の代わりにはならない、と覚えておきましょう。
B

品質を高める

Verify, don't just trust

出力を鵜呑みにしないための仕組み。6章「AI出力との向き合い方」の、日々の実践面です。

モデルと思考量を選び分ける

モデルルーティングは、タスクに応じて使うモデルを選び分けること。Claude Code の標準は上位モデルなので、普段の実装は標準のまま使い、ファイル検索や定型的な調査など「軽い仕事」を軽量モデルに回すのが現実的です。軽量モデルで失敗してやり直すと、かえって高くつくこともあります。モデルは /model で切り替えられます。

クロスレビューと反復

クロスレビューは複数AIで確認し合う手法。同じAIに観点を変えて反復させるのも効きます。

  • バグの調査をしてください
  • 前回と別の観点で調査をしてください
  • これまでの結果で、調べ足りない箇所がないか調査してください
  • これまでの結果の妥当性を検証し、優先度をつけてリスト化してください
Costクロスレビューや反復思考は効果的ですが、その分トークン（＝コスト）を多く消費します。使いどころを絞りましょう。

MCPで裏取りする

見覚えのないAPIや設定は、ハルシネーションの可能性があります。MCPで公式ドキュメントや最新仕様を参照させ、AI自身に裏取りさせてから採用します。

AIにレビューさせる

変更をコミットする前に、AI自身にもう一度チェックさせると見落としが減ります。人のレビューの前段として使いましょう。

  • /code-review … 手元の差分やPRを、バグの観点でレビューさせる
  • /security-review … 変更内容に脆弱性（入力チェック漏れ・機密情報の露出など）がないか調べさせる

深く考えさせる（思考の深さ）

最新のモデルは、答える前に考える過程を自動で挟みます。その深さは /effort で5段階（low〜max）に調整でき、1回だけ深く考えさせたいときはプロンプトに ultrathink と書きます。あわせて「複数の案を比較してから答えて」「根拠も示して」のように促すと、検討の質がさらに上がります。

Trade-off深く考えるほど時間とトークンを使います。難しい設計判断やバグ調査では上げ、単純な作業では下げるのがコツ。テストを勝手に弱めさせない等の品質ルールは 5章 を参照。
C

スケールさせる

Scale the work

大きな仕事や複雑な入力に対応するための工夫。発展的なので、まず単一セッションに慣れてから少しずつ取り入れましょう。

ファイルと画像で渡す

  • 長大・複雑な内容はプロンプトに貼らず、ファイルに書いて読み込ませる
  • エラー画面やUIデザインは画像（スクリーンショット）で渡すと、言葉で説明するより速く正確に伝わる

サブエージェントで役割分担

大きなタスクはサブエージェントに切り出して役割分担させます。調査役・実装役・レビュー役のように分けると、見通しが良くなります。サブエージェントは自分専用のコンテキストで動くため、長い調査ログでメインの会話が埋まりません。

  • よく使う役割は .claude/agents/ にファイルで定義しておくと、チームで共有できる
  • 定義ごとに使うモデルを指定できる。調査役は軽量モデル、のように分ければコストも下がる

Git worktree で並行作業

Git worktreeを使うと、1つのリポジトリから複数の作業場所を切り出し、別々のタスクを同時に進められます。作業どうしが干渉しないため、サブエージェントとの相性も良いです。

Note並行作業は強力ですが、その分管理も増えます。まず「1タスク1ブランチ」の基本に慣れてから。
D

コストを抑える

Spend fewer tokens

Claude Code は会話履歴や読み込んだファイルをすべてコンテキストとして扱うため、渡す情報が多いほどトークン（＝コスト）が増えます。必要なものだけを、必要なときに渡す——これが基本です。

対象を絞って渡す

最も効果が大きいのがこれ。修正を頼むときは、対象のファイルや関数を具体的に指定します。範囲を絞れば、関係ないファイルを読み込む無駄がなくなり、意図ズレも減ります。

✕ 曖昧「プロジェクト全体を見て、ログインのバグを直して」→ 関係ないファイルまで読み込み、トークンを浪費。修正範囲も広がりがち。
✓ 絞る「src/auth/login.ts のログイン処理だけを直して。関連するのは session.ts です」→ 必要な文脈だけを渡せて、速く・安く・正確に。
TipClaude Code では、プロンプトに @src/auth/login.ts のように @ファイルパス を書くだけで、そのファイルを対象として読み込ませられます。

コンテキストを整理する（/clear と /compact）

セッションが長いほど履歴が積み上がり、消費が増えます。/context で使用量を、/usage で利用状況を確かめながら、区切りで整理しましょう。

  • タスクが変わったら /clear … 履歴をリセット。消費削減の効果が最大
  • 会話が長くなりすぎたら /compact … 要約して引き継ぐ

定型化してキャッシュを効かせる

毎回の前提は CLAUDE.md に、頻出の作業手順はスキルに登録します。CLAUDE.md のように毎回同じ内容はキャッシュが自動で効き、同じセッション内での2回目以降のやり取りが安くなります。スキルは必要なときだけ読み込まれるので、CLAUDE.md に全部書くより軽く済みます（入力の手間が減る効果は、セッションをまたいでも有効です）。

Tipキャッシュは、モデルや思考の深さを途中で切り替えたり、/compact したりすると作り直しになります。また、セッション中に CLAUDE.md を書き換えても、/clear や再起動をするまで反映されません。
In short「手戻りを減らすこと」も立派なコスト削減です。意図を固める（プラン承認）で無駄な生成を防ぎ、モデルと思考量を選び分ける——これらはすべてトークン削減に効いてきます。

Recap — Checklist

1枚で振り返る

ここまでの原則と実践を、明日から使えるチェックリストに。迷ったら、ここへ戻ってきてください。

守る — ルール（Part Ⅰ）
  • チームで共通ルールを決め、AIにも同じ前提で作業させる
  • ルールは CLAUDE.md 等に集約し、毎回読ませる（シンプルに保つ）
  • 機密情報（APIキー・.env・本番データ）はコンテキストに渡さない
  • 絶対に止めたい操作は、お願いでなく拒否ルール・フックで仕組み化する
  • DBのテーブル・スキーマ変更は承認制＋人の確認
  • 頼んでいないリファクタリングをさせない／テストを勝手に弱めさせない
  • AIの出力は「たたき台」。最終判断と重要処理のレビューは人が行う
活かす — 実践（Part Ⅱ）
  • 実装前に計画を出させ、承認してから着手（プラン承認・計画モード）
  • 実装は標準モデル、軽い調査は軽量モデルのサブエージェントへ
  • 見覚えのないAPIや設定は MCP 等で裏取りしてから採用
  • コミット前に /code-review でAIにも確認させる
  • 難所は /effort を上げ、単純作業では下げる（コスト意識）
  • 修正は対象ファイルを絞って渡す＝無駄なトークンを減らす
  • タスクが変わったら /clear、長引いたら /compact で整理
